# BenchEval 愿景与设计原则

> **一句话目标**：给定**任意**测试集，自动跑完「评估 → 反馈合成 → 质量过滤」这套数据飞轮，产出的合成数据经过 SFT / RL 训练后，能**显著提升**被训练模型在该测试集上的表现——全程尽量无人工介入。

---

## 1. 我们要解决的问题

这套代码的前身是针对 ToM（Theory-of-Mind）系列数据集做的「评估 + 反馈 + 过滤」专用流程。它已经证明了一个闭环是有效的：

```
评估被测模型 → 找到它答错的题 → 诊断它弱在哪 → 针对性合成新训练数据 → 过滤掉低质/泄漏样本 → 训练 → 再评估
```

但目前这套流程在很多地方**绑死了 ToM 的领域知识**：维度字段映射写死了 `ability / condition_type / order_N`，合成 prompt 里塞满了 ToM 认知操作，judge rubric 是为社会认知题定制的。换一个数据集（比如数学、代码、通用 QA），就得改一堆代码。

**BenchEval 的目标，是把这套被验证有效的飞轮从 ToM 解耦出来，变成数据集无关的通用框架。** 用户拿来一个全新的测试集，不写代码、不改 prompt，就能跑完整条飞轮并看到指标提升。

---

## 2. 北极星指标

唯一衡量成功的标准：

> **合成数据训练后，被测模型在「用户给定测试集」上的指标，相对训练前有显著、可复现的提升。**

不是「合成了多少条数据」，不是「流程跑通了」，而是**测试集上的真实提升**。一切流程设计都要服务于这个终点。

---

## 3. 三条核心原则

### 原则一：流程自动化（尽可能去人工）

用户的输入边界应当**收敛到最小**：

- 建立环境（装依赖、配 API key）
- 提供**被训练模型**（本地 vLLM 或云端 API）
- 提供**测试集**（标准化 parquet，或可被自动转换的原始格式）
- 提供**强 teacher 模型的 API**（用于诊断、合成、判分）

剩下的全部自动化：评估 → 诊断薄弱维度 → 合成 → 去重过滤 → （触发训练）→ 再评估，**迭代式自动进行**，直到指标收敛或达到轮数上限。

人工成分要持续往零逼近。每当流程里出现「需要人改配置 / 改 prompt / 手工标注」的环节，都要问一句：**这一步能不能自动推断？**

> **当前与目标的差距**（已知的人工卡点，是后续工作的靶子）：
> - 维度字段（`get_dimension_key`）目前对每个数据集硬编码 → 目标是从 `meta` 自动发现分组字段。
> - 合成 schema / prompt（`SYNTHESIS_SCHEMA_REGISTRY`、`DATASET_SKILL_REGISTRY`）目前每个数据集手写 → 目标是从测试集样本自动推断题型结构与领域说明。
> - judge rubric 目前数据集自带 → 目标是开放题判分尽量走免模型的 `f1`，或自动生成 rubric。

### 原则二：流程轻量化（非必要不加流程）

每一个阶段、每一个中间产物、每一份配置，都必须能回答「不加它会怎样」。如果答案是「没什么本质影响」，那就**不加**。

- 优先**复用**已有模块，而不是新写一份（见 `docs/module_reference.md` 的复用速查表）。
- 判分能用规则（MCQ 的 `\boxed{}` 提取、开放题的 F1）就不调模型，省 token、去依赖。
- 阶段开关要支持**优雅降级**：filter 的 `passk_enabled / answerability_enabled / shortcut_enabled / repair_enabled` 任一关掉，流程仍能跑通，只是少一层筛查。
- 不为了「看起来完整」而堆叠中间步骤。每条流水线的阶段数要尽量少。

### 原则三：流程可视化（让使用者看得见）

使用者要能**直观感受到**飞轮在转、模型在变强：

- **流程流转可见**：当前跑到哪个数据集、哪个阶段、处理了多少样本，要有清晰进度。
- **指标提升可见**：训练前 vs 训练后、第 N 轮 vs 第 N+1 轮，在给定测试集上的准确率/分组指标，要能一眼看到提升曲线。
- 复用现有的 `src/visualization`（数据集无关出图）和 `report/`（Markdown 表格 / HTML 报告），把「迭代提升」做成一等公民的视图。

## 4. 目标使用流程（用户视角）

理想状态下，用户只做这几件事：

```bash
# 1. 建环境
pip install -r requirements.txt

# 2. 一份配置：被训练模型 + 测试集 + teacher 模型 API
#    （后续目标：合并成单一 orchestrator 配置）
vim experiment_config.yaml      # 被测模型 + 测试集
vim feedback/config.yaml        # teacher 模型（合成）
vim filter/config.yaml          # teacher / 弱模型（质量过滤）

# 3. 一键迭代
python run_eval.py        # 评估当前模型 → 拿到 bad case 和基线指标
python run_feedback.py    # 诊断薄弱维度 → 合成新数据
python run_filter.py      # 质量过滤 + 防泄漏 → 得到干净训练集
#   → SFT / RL 训练（外部）
#   → 回到 run_eval.py，看指标是否提升
```

**终极目标**：上面的多次手动调用收敛成**一个 orchestrator 入口**，自动循环「评估→合成→过滤→训练→再评估」，并实时输出指标提升视图。这是 BenchEval 区别于「一堆脚本」的关键。

## 5. 三条流水线如何咬合

```
                   ┌─────────────────────────────────────────────┐
                   │              用户给定的测试集                  │
                   └─────────────────────────────────────────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                                              ▼
   ┌─────────────────────┐                       ┌─────────────────────┐
   │  run_eval.py 评估    │  bad case + 基线指标   │  防泄漏守门员         │
   │  predict→judge→出图  │ ─────────────────────▶│ (LSH 比对测试集)     │
   └─────────────────────┘                       └─────────────────────┘
              │                                              ▲
              │ prediction.jsonl                             │
              ▼                                              │
   ┌─────────────────────┐      合成候选        ┌─────────────────────┐
   │ run_feedback.py 合成 │ ───────────────────▶│ run_filter.py 过滤   │
   │ 诊断维度→生成新题    │                      │ 决策树评估+自动修复  │
   └─────────────────────┘                      └─────────────────────┘
                                                           │
                                                           ▼
                                                  干净训练集 parquet
                                                           │
                                                           ▼
                                                  SFT / RL 训练（外部）
                                                           │
                                                           └──▶ 回到 run_eval.py（下一轮）
```

- **评估**（`run_eval.py`）：产出基线指标 + `prediction.jsonl`（bad case 的来源）。
- **合成**（`run_feedback.py`）：吃 bad case，诊断薄弱维度，合成新题。
- **过滤**（`run_filter.py`）：对合成数据做质量评估（太简单/无法回答/可走捷径）+ 自动修复 + 防测试集泄漏。
- **报告/可视化**：贯穿全程，把指标和流程流转可视化。

三条流水线已经各自跑通，**BenchEval 阶段的工作是把它们的「数据集专属假设」抽掉，并用一个 orchestrator 串成自动迭代循环。**

---

## 6. 设计哲学小结

| 原则 | 一句话 | 反面教材 |
|---|---|---|
| 自动化 | 用户只给「模型+测试集+teacher API」，其余推断 | 每个新数据集都要手写维度映射和合成 prompt |
| 轻量化 | 非必要不加流程，能复用就不重写 | 为了完整堆一堆没人看的中间产物 |
| 可视化 | 流程流转 + 指标提升都看得见 | 跑完只在终端打几行日志 |

> 维护本文件的人请记住：当一个改动让「用户需要手动做的事」变多，或让「跑通一个新数据集」变难，它大概率违背了 BenchEval 的初衷，应当重新考虑。
